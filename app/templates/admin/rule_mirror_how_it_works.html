How the Rule Git Mirror Works

An off-by-default, admin-configured feature that mirrors every active, public rule into a plain git repository — one folder per rule — so anyone who wants "all the rules" can git clone instead of going through the app or API.

Overview

Rule created / updated / deleted
in Rulezet
→
Sync job
(scheduled or "Run now")
→
One commit per rule
pushed to the mirror repo

There is no separate "history" folder — a rule's file lives at the same path for its whole life, and every content change is a new commit on that path. git log --follow on any rule's file is its full version history, for free.

Repository layout

rules/
  <format>/                  yara, sigma, suricata, splunk, elastic, kql, ...
    <shard>/                 first 2 hex chars of the rule's uuid
      <uuid>/
        rule.<ext>             the rule's content, correct extension per format
        metadata.yaml           title, author, license, description, tags,
                                 ATT&CK techniques, CVEs, rulezet_url, ...
metadata.yaml's license_verified flag is true only when the rule's license matches a small permissive allow-list (MIT, Apache-2.0, GPL-*, CC-*, ...). Every rule is mirrored regardless — this just makes an unclear or non-permissive license visible instead of silent.

How a sync works

  1. First sync takes every active rule's current content — it does not replay past edits. Git history for the mirror starts the day it goes live.
  2. Every sync after that is incremental: only rules created/updated/deleted since the last sync are touched — one commit per changed rule, one git rm per deleted rule.
  3. A sync can be triggered two ways: the settings page's "Run now" button (a one-off background job, same as any other admin action), or a recurring schedule created in Workflows ("Rule Git Mirror — sync").

Security model

This feature pushes to a third-party service using a stored credential — read this section before enabling it.
  • Off by default, admin-only, per instance. Nothing is enabled by install/update scripts — an admin has to explicitly turn it on and configure a repo.
  • Its own token, on purpose. Use a token dedicated to this feature — not the GITHUB_TOKEN used for GitHub rule import — ideally a fine-grained GitHub PAT restricted to just the mirror repo (contents: read & write, nothing else).
  • The token is never shown again once saved. The settings page only ever shows a masked placeholder; changing it means entering a new value, not revealing the old one.
  • The token never appears in a process list. It's written straight into the local mirror clone's .git/config (a plain file write) immediately before a push, then cleared right after — never passed as a command-line argument to git.
  • Only public content is mirrored — the same rules an anonymous visitor could already browse on this instance.

Set it up on your own instance

Five steps, from a blank GitHub repo to a running mirror.

1
Create (or pick) a GitHub repository to hold the mirror — it can be completely empty. Public if you want it clonable by anyone, private if it's just for your own team.
2
Create a token scoped to just that repository. On GitHub: Settings → Developer settings → Fine-grained personal access tokens → New token, "Only select repositories" → your mirror repo, permission Contents: Read and write, nothing else.
3
Open Admin → Rule Git Mirror, enter the repository URL, branch (defaults to main), and the token from step 2. Save.
4
Toggle "Enabled" and click "Run now" for the first sync. Track its progress on the Jobs page — for a large instance this can take a while the first time (it walks every active rule).
5
Schedule ongoing syncs in Workflows — create a task of type "Rule Git Mirror — sync" with whatever recurrence you want (weekly is a reasonable default). From then on, new/changed/ deleted rules keep the mirror current automatically.
That's it — disable the feature any time by toggling it off on the settings page; nothing further gets pushed, and nothing already mirrored is touched.
